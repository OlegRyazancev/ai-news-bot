# Stage 3 — Хранение и дедупликация

Checklist этапа **3. Хранение и дедупликация**. Канонические цель и критерий завершения находятся в [ROADMAP.md](../ROADMAP.md), фактическое состояние — в [CURRENT_STATE.md](../CURRENT_STATE.md), принятые решения — в [DECISIONS.md](../DECISIONS.md).

## Статус

✅ Завершено — реализация, проверки агента и ручная приёмка пользователем выполнены

## Цель

Надёжно сохранять нормализованные статьи в PostgreSQL без дублей и возвращать свежие материалы через Telegram-команду `/latest`.

## Scope

### In scope

- Сервис персистентности, преобразующий `NormalizedArticle` в данные `NewsArticle`.
- Insert-only сохранение по точному нормализованному URL с опорой на уникальное ограничение PostgreSQL.
- Безопасная обработка повторов как внутри одного batch, так и между последовательными циклами.
- Подключение персистентности к существующему downstream handler цикла сбора.
- Итоговая статистика сохранения: получено, создано и пропущено как дубли.
- Получение ограниченного списка последних статей из PostgreSQL по `publishedAt`.
- Реальная команда `/latest` с безопасным HTML-форматированием, ссылками и понятным empty state.
- Unit-тесты mapping, дедупликации, сортировки и форматирования.
- Runtime-проверка с реальными RSS/Atom-статьями, PostgreSQL и Telegram.

### Out of scope

- Обновление уже сохранённой статьи при повторном URL.
- Расширенная канонизация URL, удаление tracking-параметров и дедупликация похожих материалов по содержимому.
- LLM-суммаризация, relevance scoring и тематическая классификация.
- Пагинация и интерактивная навигация в `/latest`.
- Retention policy, архивирование и очистка старых статей.
- Создание migration baseline: модель `NewsArticle` уже определена и применялась через `prisma db push`.

## Реализация

- [x] Создать отдельный сервис/repository для сохранения нормализованных статей через Prisma.
- [x] Явно преобразовать все обязательные и опциональные поля `NormalizedArticle` в `NewsArticle` без записи `sourceId`, которого нет в текущей схеме.
- [x] Реализовать batch insert с обработкой конфликтов уникального URL без падения всего цикла.
- [x] Возвращать статистику количества полученных, созданных и пропущенных статей.
- [x] Не обновлять существующую запись и не перезаписывать её поля при повторном URL.
- [x] Подключить сохранение к `NewsCollectionRunner` через существующий асинхронный article handler.
- [x] Логировать только безопасную агрегированную статистику сохранения без полного текста статей.
- [x] Сохранить изоляцию ошибок источников и возможность последующих scheduler-циклов после ошибки БД.
- [x] Реализовать запрос последних статей с детерминированной сортировкой по `publishedAt` и ограничением размера ответа.
- [x] Заменить заглушку `/latest` данными PostgreSQL.
- [x] Экранировать внешние значения для Telegram HTML и не превышать допустимый размер сообщения.
- [x] Удалять обрамляющие Markdown-маркеры из новых RSS-заголовков и при выводе ранее сохранённых записей.
- [x] Реализовать понятный ответ, если сохранённых статей нет.
- [x] Реализовать безопасную обработку ошибки чтения БД без утечки деталей пользователю.
- [x] Добавить unit-тесты persistence-сервиса, включая повторы внутри batch и между вызовами.

## Риски

- Exact URL дедупликация не объединяет URL с разными tracking-параметрами или зеркала одной статьи.
- Одновременные insert-операции должны полагаться на ограничение БД, а не только на предварительный SELECT.
- Внешние title/source могут содержать HTML-символы и требуют экранирования перед Telegram.
- Недоступность PostgreSQL не должна навсегда останавливать scheduler или скрываться успешным логом сбора.
