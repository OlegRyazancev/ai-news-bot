# /stage-start Command

## Назначение

Начать новый крупный этап из канонического `docs/ROADMAP.md`: провести анализ, создать или актуализировать единственный checklist этапа, подготовить план и остановиться до подтверждения реализации пользователем.

## Workflow

### 1. Прочитать контекст

Прочитай:

- `AGENTS.md`;
- `docs/PROJECT.md`;
- `docs/ARCHITECTURE.md`;
- `docs/CURRENT_STATE.md`;
- `docs/DECISIONS.md`;
- `docs/BACKLOG.md`;
- `docs/ROADMAP.md`;
- `docs/ROADMAP_VISUAL.md`.

Проверь `git status` и изучи релевантный существующий код.

### 2. Определить целевой этап

- Используй раздел **«Текущий фокус»** канонического `docs/ROADMAP.md`.
- Не выбирай этап только как «первый незавершённый», если roadmap задаёт другой фокус.
- Сверь номер, название, статус, цель, критерий завершения и зависимости этапа.

### 3. Провести stage-specific анализ

Анализ должен определить:

- что уже реализовано и может быть переиспользовано;
- что фактически Verified / Build-Verified / Runtime-Verified;
- чего не хватает до критерия завершения;
- какие части кода предположительно будут затронуты;
- какие зависимости этапа уже выполнены, а какие нет;
- какие риски и edge cases видны;
- что входит в scope;
- что явно находится вне scope;
- есть ли архитектурные решения, требующие Decision Gate.

### 4. Применить Decision Gate

Если требуется существенное решение, отсутствующее в `docs/DECISIONS.md`:

1. Остановись до выбора реализации.
2. Опиши вопрос и 2–3 разумных варианта.
3. Для каждого варианта укажи преимущества, недостатки и влияние на этап.
4. Дождись решения пользователя и затем обнови `docs/DECISIONS.md`.

### 5. Найти или создать checklist

Ищи checklist в `docs/checklists/` по номеру этапа.

- Имя: `<двузначный номер>-<короткий-slug>.md`.
- Для этапа допускается максимум один checklist.
- Если checklist существует, проверь его актуальность и внеси только необходимые изменения.
- Если checklist отсутствует, создай его только после завершения анализа.
- Не создавай checklist следующих этапов заранее.
- Не веди changelog внутри checklist — историю хранит Git.

Минимальная структура нового checklist:

```markdown
# Stage N — <название>

## Статус

⬜ Запланировано / 🟡 В работе / ✅ Завершено

## Цель

## Scope

### In scope

### Out of scope

## Preconditions

## Реализация

## Build Verification

## Runtime Verification

## Acceptance

## Открытые вопросы
```

Checklist основывается на критерии завершения roadmap, текущем состоянии, backlog, архитектуре, решениях, фактическом коде и зависимостях этапа. Build Verification не заменяет Runtime Verification.

### 6. Подготовить план реализации

- Сформируй последовательность крупных изменений и проверок.
- Не расписывай checklist до уровня каждой строки кода.
- Не начинай реализацию.

### 7. Выдать Stage Kickoff Report

Используй формат:

```text
Stage:
Current state:
Already available:
Missing:
In scope:
Out of scope:
Decisions required:
Risks:
Checklist:
Implementation plan:
```

### 8. Остановиться

После `/stage-start` нельзя менять application code или начинать реализацию, пока пользователь явно её не подтвердит.

## Rules

- Разрешено создать или актуализировать только checklist целевого этапа и необходимые source-of-truth документы.
- Не отмечай непроверенные результаты как выполненные.
- Не выполняй commit или push без явного запроса пользователя.
