Организуй один предварительный архитектурный анализ через project agent `architect` с ограниченным orchestration-level Model Fallback.

Команда выполняется в текущей Developer-сессии. Не переключай основной agent или модель Developer и не создавай background child. Один запуск `/architect` остаётся одним архитектурным анализом независимо от количества model attempts.

## Фиксированный план

1. Проверь наличие описания архитектурной задачи, цели и ограничений, затронутых компонентов, известных архитектурных решений, конкретных вопросов к Architect и минимально необходимого проектного контекста. Значение `unknown` допустимо для неизвестных решений, но отсутствие обязательного поля не заменяй предположением.
2. Определи минимальный набор уже переданного контекста и точных project-relative путей, которые действительно нужны для анализа. Не выполняй полный анализ репозитория, не собирай Git snapshot и не используй `glob` или `grep` для расширения scope.
3. Выполни локальный security preflight подготовленного текстового контекста и всех выбранных путей. До завершения path preflight не читай выбранные context-файлы.
4. Каждый прошедший path preflight context-файл прочитай через `read` не более одного раза для полной локальной проверки. Не помещай полное содержимое большого документа в payload без доказанной необходимости.
5. Выполни content preflight переданного текста и полного прочитанного содержимого. Для каждого безопасного файла локально рассчитай SHA-256 exact bytes без вывода содержимого и добавь в manifest путь, hash и назначение. При любом blocker остановись до вызова Architect.
6. Подготовь краткий непосредственно необходимый `context_summary`. Только если для точного исторического факта недостаточно ссылки на текущий файл, один раз зафиксируй минимальный проверенный фрагмент вместе с его path, locator и SHA-256.
7. Один раз сформируй и сериализуй компактный `architecture_payload`, сохрани точную сериализованную строку и рассчитай `architecture_payload_sha256` по её UTF-8 bytes. После этого не изменяй, не копируй вручную и не пересобирай строку между model attempts.
8. Запусти описанную ниже цепочку через один и тот же project agent `architect`. Каждый вызов выполняй в foreground, в новой child session, без `sessionID` предыдущей попытки и с явным model override. Передавай сохранённую строку напрямую и не запускай другие subagents.
9. Если до вызова доступен hash exact prompt argument, сравни его с `architecture_payload_sha256`. При несовпадении остановись с `IMMUTABLE_CONTEXT_VIOLATION` до отправки модели. Если runtime metadata после вызова предоставляет сохранённый explicit prompt, также проверь его hash и при несовпадении не используй результат и не выполняй следующий fallback.
10. При успешном ответе немедленно останови цепочку и оцени результат в Developer-контексте. Недостаточное качество содержательного ответа не является основанием для fallback.

Если обязательного контекста недостаточно до вызова или Architect вернул `ARCHITECTURE_CONTEXT_REQUIRED`, остановись без fallback, перечисли недостающие сведения и передай пользователю точные вопросы.

## Контракт вызова

Developer подготавливает:

- `task`: описание архитектурной задачи;
- `goal`: цель изменения;
- `constraints`: явные ограничения;
- `components`: затронутые компоненты или границы, в которых их нужно определить;
- `decisions`: известные архитектурные решения либо `unknown`;
- `questions`: конкретные вопросы к Architect;
- `context`: краткий непосредственно необходимый контекст и точный manifest разрешённых project-relative путей;
- дополнительные требования из `$ARGUMENTS`.

Ожидаемый минимальный формат:

```text
task=<архитектурная задача>
goal=<цель>
constraints=<ограничения>
components=<затронутые компоненты или границы определения>
decisions=<известные решения или unknown>
questions=<конкретные вопросы>
context=<краткий контекст и точные безопасные пути>
```

Не требуй полного чтения репозитория. Не дублируй инструкции `.opencode/agents/architect.md` в `architecture_payload`: передавай задачу, ограничения, вопросы и необходимый контекст.

Контекст задачи от Developer:

$ARGUMENTS

## Security preflight

Security preflight выполняется локально в Developer до формирования `architecture_payload` и до любого вызова внешней модели. Он применяется к исходным требованиям, краткому контексту, фиксируемым фрагментам и полному содержимому каждого файла, который Developer разрешает Architect читать.

### Path preflight

Проверь каждый точный путь из подготовленного контекста. Считай потенциально секретными как минимум:

- реальные env-файлы: `.env`, `.env.local`, `.env.production` и другие `.env.*`, кроме явно шаблонных `.env.example`, `.env.sample` и `.env.template`;
- пути и файлы с именами `credentials`, `credential`, `secrets`, `secret`, `service-account` и очевидными производными;
- приватные ключи и key stores: `id_rsa`, `id_ed25519`, `*.pem`, `*.key`, `*.p12`, `*.pfx`, `*.jks`;
- credential-файлы в `.ssh`, `.aws`, `.azure`, `.gcp` и аналогичных каталогах;
- `.git` и его содержимое;
- пути за пределами проекта.

Не читай заблокированный путь. Если путь потенциально секретный, недоступен, оказался каталогом или бинарным файлом, output truncated либо содержимое нельзя полностью проверить, не вызывай Architect. Сообщи только безопасный путь и категорию blocker без значения секрета.

### Content preflight

Проверь исходный текстовый контекст, фиксируемые фрагменты и полное прочитанное содержимое выбранных файлов. Ищи очевидные признаки утечки:

- PEM/private-key headers;
- bearer/basic authorization values или URL со встроенными credentials;
- известные token/key prefixes;
- JWT-подобные значения;
- непустые высокоэнтропийные значения рядом с `api_key`, `apikey`, `token`, `secret`, `password`, `private_key`, `client_secret` и аналогичными именами.

Не считай секретом очевидные placeholders и ссылки на environment variable без значения. Не выводи совпавшую строку или значение и не пытайся автоматически исправлять, удалять либо маскировать секрет. При неоднозначном совпадении остановись fail-closed до вызова Architect.

Проверка эвристическая: успешный preflight снижает риск, но не гарантирует обнаружение всех конфиденциальных данных.

## Immutable architecture context

Один раз сформированный компактный `architecture_payload` содержит в фиксированном порядке:

- исходные `task`, `goal`, `constraints`, `components`, `decisions` и `questions`;
- дополнительные требования из `$ARGUMENTS`;
- краткий `context_summary` без полного пересказа документов;
- `context_manifest` с точными разрешёнными путями, назначением и SHA-256 проверенного содержимого каждого файла;
- только необходимые `captured_fragments` вида `path + locator + fragment_sha256 + content`, если ссылка на актуальный файл недостаточна;
- инструкцию Architect читать только пути из `context_manifest`, а при необходимости другого файла вернуть `ARCHITECTURE_CONTEXT_REQUIRED` с точным путём и причиной;
- явно отмеченные ограничения и неизвестные сведения.

Не включай полное содержимое больших документов только ради удобства модели. Предпочитай manifest и самостоятельное чтение Architect; зафиксированный фрагмент используй только для минимального неизменяемого исторического контекста.

Сериализуй payload ровно один раз с однозначным порядком полей и сохрани полученную строку без последующего редактирования. Рассчитай `architecture_payload_sha256` по UTF-8 bytes этой строки. Каждой model attempt передавай эту сохранённую строку напрямую: не перечитывай файлы, не копируй документы повторно, не добавляй факты и не реконструируй prompt вручную.

Если можно получить exact prompt argument до отправки, его SHA-256 обязан совпасть с `architecture_payload_sha256`. При несовпадении верни `IMMUTABLE_CONTEXT_VIOLATION`, укажи только ожидаемый и фактический hash и не вызывай модель. Если доступен только persisted prompt после вызова, выполни post-call проверку; несовпадение делает результат непригодным и запрещает следующий fallback.

После ответа проверь доступные tool-call metadata Architect. Чтение пути вне `context_manifest` означает `ARCHITECTURE_CONTEXT_VIOLATION`: не используй такой результат и не переключай модель ради другого содержательного ответа. Если metadata tool calls недоступны, явно укажи, что соблюдение manifest не проверено технически.

## Техническое ограничение OpenCode

Markdown-команда OpenCode и текущий `subagent` tool принимают inline `prompt` для каждого отдельного вызова и не предоставляют нативный immutable prompt object или ссылку на ранее сериализованную строку. Поэтому без отдельного wrapper/plugin нельзя программно гарантировать, что Developer не реконструирует аргумент между tool calls.

Не создавай wrapper, plugin, временный файл, новую зависимость или отдельное хранилище контекста для обхода этого ограничения. Команда также не может динамически сузить permissions Architect до manifest: запрет дополнительных путей обеспечивается инструкцией и доступным post-call аудитом tool metadata, а не отдельным permission sandbox.

Локальный SHA-256 подтверждает сохранённую сериализацию, но гарантирует фактически переданные bytes только если runtime позволяет проверить exact tool argument до отправки. Post-call hash persisted user-message обнаруживает расхождение, но не предотвращает уже состоявшуюся отправку. Не заявляй о подтверждённой byte-for-byte идентичности, если hashes фактических explicit prompt каждой попытки не получены и не совпали.

Architect самостоятельно читает только предварительно проверенные пути из `context_manifest`. Manifest hash фиксирует проверенную Developer версию, но Architect не может подтвердить этот hash только через `read`; если файл изменился после preflight, фактически прочитанное содержимое может отличаться. Одинаковый prompt не создаёт атомарный снимок файловой системы и не гарантирует одинаковый полный runtime-контекст child sessions. Укажи это ограничение при fallback или возможном изменении working tree.

## Цепочка моделей

На один запуск `/architect` допускается максимум три foreground-вызова Architect, строго в этом порядке:

1. `google/gemini-3.5-flash` — Primary;
2. `google/gemini-3.5-flash-lite` — Fallback 1;
3. `openai/gpt-5.6-luna-fast` — Fallback 2.

Всегда начинай с Primary. Каждую модель вызывай максимум один раз. При успешном завершении любой попытки немедленно останови цепочку. Не возвращайся к уже вызванной модели и не создавай циклические или неограниченные retry.

Каждый вызов должен быть эквивалентен:

```text
subagent(
  agent=architect,
  model=<текущая модель цепочки>,
  background=false,
  prompt=<сохранённая сериализованная строка architecture_payload без реконструкции>
)
```

Model override применяется только к child session. Не переключай agent или model основной Developer-сессии и не изменяй `.opencode/agents/architect.md`.

Перед попыткой `openai/gpt-5.6-luna-fast` допускается только уже существующее account-based OAuth-подключение OpenAI. Не создавай и не переключай provider connection, не запрашивай и не читай credentials, не используй отдельный API key. Если безопасные runtime metadata не подтверждают `credential/oauth`, Luna Fast не вызывай и зафиксируй `not attempted: account-based OAuth not confirmed`.

## Gate переключения модели

Fallback разрешён только когда foreground-вызов subagent завершился ошибкой и доступные структурированные runtime metadata однозначно подтверждают allowlisted provider request error:

- исчерпание квоты или явный quota code, например `RESOURCE_EXHAUSTED`/`QUOTA_EXCEEDED`;
- HTTP `429`;
- HTTP `500`, `502`, `503` или `504`, явно классифицированный как временная недоступность провайдера;
- явная транспортная ошибка provider request: timeout, connection reset/refused, временная DNS/network/TLS-недоступность.

HTTP `403` разрешает fallback только при отдельном явном structured quota indication. Один статус `403`, произвольный текст ошибки или предположение о квоте недостаточны.

Не классифицируй ошибку исключительно по текстовому сообщению или содержательному ответу Architect. Не включай raw provider message/payload в следующую попытку или итоговый отчёт. Для причины переключения сохраняй только безопасную категорию, HTTP status и allowlisted error code, если они доступны.

Не выполняй fallback при:

- успешном архитектурном анализе;
- `ARCHITECTURE_CONTEXT_REQUIRED`;
- `IMMUTABLE_CONTEXT_VIOLATION` или чтении пути вне `context_manifest`;
- недостаточном качестве, неполноте или спорности содержательного ответа;
- ошибке или неполноте входного контекста;
- ошибке авторизации/credentials, включая HTTP `401` и generic HTTP `403`;
- неизвестной, неоднозначной или неклассифицированной ошибке;
- interrupted/cancelled child session, пустом результате или отсутствии достаточных structured metadata;
- достижении лимита `8` model steps.

Если результат неоднозначен, остановись без следующего вызова и сообщи конкретный blocker. Fallback attempt остаётся частью одного архитектурного анализа и не является повторным анализом с новым контекстом.

Если все три модели завершились только подтверждёнными allowlisted provider errors, верни `ARCHITECTURE_UNAVAILABLE` и безопасный список попыток. Если Luna Fast не вызвана из-за неподтверждённого account-based OAuth после подтверждённой недоступности обеих Gemini-моделей, также верни `ARCHITECTURE_UNAVAILABLE`, отметив третью модель как `not attempted`, а не как provider failure.

## Контроль качества результата

После успешного ответа Developer проверяет:

- даны ли ответы на поставленные вопросы;
- рассмотрена ли применимость существующих ADR;
- выявлены ли существенные архитектурные риски и failure modes;
- корректно ли разграничены гарантии приложения, транзакционной БД и внешних систем;
- для каждого существенного partial failure подтверждается ли заявленная гарантия конкретным механизмом, а неопределённый исход внешнего вызова не описан как гарантированно восстановимый;
- не выданы ли best-effort release/recovery, последующий stale recovery или требующее доступной БД условное обновление за гарантированное восстановление;
- содержит ли отчёт явный и обоснованный Architecture Decision Gate;
- не запрашивает ли Architecture Decision Gate повторное согласование уже принятого и применимого решения без нового требования, конфликта, изменившегося ограничения или существенного незакрытого выбора;
- отделены ли подтверждённые факты от предположений;
- отсутствуют ли необоснованные абсолютные гарантии;
- использовал ли Architect только пути из `context_manifest`, если runtime metadata позволяют это проверить.

Если применимое решение уже зафиксировано и новых оснований для выбора нет, Developer фиксирует `новый Architecture Decision Gate не требуется` и не просит пользователя повторно подтверждать это решение. Если ответ содержательный, но неполный или содержит перечисленные необоснованные гарантии, не переключай модель автоматически. Зафиксируй пробелы и ограничения, сформулируй недостающие сведения или передай вопросы пользователю. Architect не принимает окончательных архитектурных решений; ответственность за решение и реализацию остаётся у Developer и пользователя.

## Итоговый отчёт

После остановки цепочки обязательно укажи:

- фактически использованную для результата модель или `none`;
- выполнялся ли fallback;
- последовательность попыток с outcome каждой модели;
- безопасные причины каждого переключения;
- `architecture_payload_sha256` и статус проверки hashes фактических explicit prompt каждой попытки;
- результат архитектурного анализа либо `ARCHITECTURE_CONTEXT_REQUIRED`, `ARCHITECTURE_UNAVAILABLE` или конкретный blocker;
- открытые вопросы и Architecture Decision Gate;
- ограничения, включая отсутствие атомарного filesystem snapshot, непроверенные аспекты и выявленные пробелы качества.

Не включай secrets, credentials или raw provider payload. Явно напомни, что это bounded orchestration Developer, а не нативный гарантированный fallback OpenCode: механизм видит только ошибки, возвращённые foreground subagent call с достаточными structured metadata, и не восстанавливает прерванную child session.
