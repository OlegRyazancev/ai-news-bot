# /stage-status Command

## Назначение

Быстро восстановить текущий рабочий контекст: показать активный этап, подтверждённые результаты, точку остановки, одно следующее действие, реальные блокеры, релевантные открытые решения и состояние Git.

Команда является строго **read-only**.

## Источники истины

Прочитай:

1. `docs/ROADMAP.md` — текущий фокус, точный статус этапа и следующий крупный milestone.
2. `docs/CURRENT_STATE.md` — фактически подтверждённые build/runtime результаты.
3. Checklist текущего этапа из `docs/checklists/` — выполненные и открытые обязательные пункты.
4. `docs/BACKLOG.md` — ближайшие задачи и практический следующий шаг.
5. `docs/DECISIONS.md` — открытые решения, относящиеся к текущему или ближайшему этапу.
6. `git status --short` — локальные staged, unstaged и untracked изменения.

Не используй ожидания или существование кода как замену фактической верификации.

## Workflow

### 1. Определить текущий этап

- Используй раздел **«Текущий фокус»** канонического `docs/ROADMAP.md`.
- Не выбирай этап только как первый незавершённый.
- Возьми точные номер, название и статус из соответствующего раздела roadmap.
- Возьми следующий крупный milestone из раздела «Текущий фокус».

Если текущий этап нельзя определить однозначно, не угадывай: укажи `Недостаточно подтверждённых данных` и назови отсутствующий или противоречивый источник.

### 2. Найти checklist этапа

- Ищи в `docs/checklists/` файл с двузначным номером текущего этапа.
- Если найден ровно один checklist, используй его для определения точки остановки.
- Если checklist отсутствует, явно сообщи об этом.
- Если для этапа найдено несколько checklist, сообщи о нарушении процесса и не выбирай один из них молча.
- Не создавай и не изменяй checklist.

### 3. Определить точку остановки

Кратко сопоставь `ROADMAP.md`, `CURRENT_STATE.md` и checklist:

- последние фактически подтверждённые результаты;
- первый или наиболее актуальный незавершённый обязательный пункт;
- недостающую проверку из раздела агента или ручную проверку пользователя;
- завершён ли этап по checklist и критерию roadmap.

Не считай пункт завершённым только потому, что код существует. `Build-Verified` не означает `Runtime-Verified`.

Если источники противоречат друг другу, ничего не исправляй: явно покажи рассинхронизацию.

### 4. Определить одно следующее действие

Дай ровно одно конкретное действие, выбранное по фактическому состоянию. Приоритет:

1. Устранить рассинхронизацию или недостаток обязательных данных.
2. Принять блокирующее архитектурное решение.
3. Если у активного этапа нет checklist — вызвать `/stage-start`.
4. Продолжить конкретный открытый обязательный пункт checklist.
5. Выполнить недостающую проверку агента либо передать пользователю точный открытый пункт его ручной проверки.
6. Если все пункты выполнены — вызвать `/stage-close`.
7. Если текущий этап уже завершён, а следующий ещё не начат — вызвать `/stage-start` для следующего этапа.

Не выдавай список следующих задач вместо одного действия.

### 5. Проверить блокеры и решения

- Показывай только реальные блокеры, подтверждённые документами или отсутствующим обязательным checklist/verification.
- Из `docs/DECISIONS.md` показывай только открытые решения, непосредственно относящиеся к текущему или ближайшему этапу.
- Не перечисляй все будущие нерешённые вопросы проекта.
- Если блокеров или релевантных открытых решений нет, напиши `Нет.`

### 6. Проверить Git

Выполни только:

```bash
git status --short
```

Кратко укажи:

- working tree clean или есть изменения;
- количество staged изменений;
- количество unstaged изменений;
- количество untracked файлов/директорий;
- общий тип затронутых файлов, если это видно из статуса.

Не выводи полный diff. Не выполняй `git add`, commit или push.

## Формат ответа

Ответ должен быть коротким и иметь структуру:

```markdown
# Stage Status

## Текущий этап

<номер>. <точное название из ROADMAP.md>

Статус: <точный статус из ROADMAP.md>

## Где остановились

- <последние подтверждённые результаты>
- <текущая незавершённая точка или «Этап завершён»>

## Следующий шаг

<одно конкретное рекомендуемое действие>

## Блокеры

<реальные блокеры или «Нет.»>

## Открытые решения

<релевантные решения или «Нет.»>

## Git

<clean или краткая сводка staged / unstaged / untracked>

## Далее

<следующий крупный milestone из ROADMAP.md>
```

## Завершённый этап

Если текущий этап завершён:

- явно напиши `Этап завершён`;
- не предлагай продолжать закрытые пункты;
- если следующий этап ещё не стартовал, рекомендуй `/stage-start`;
- наличие незакоммиченных изменений покажи в разделе Git, но ничего не коммить автоматически.

## Неполные или противоречивые данные

Если нельзя достоверно определить текущий этап, точку остановки, Runtime Verification или следующий шаг:

- напиши `Недостаточно подтверждённых данных`;
- перечисли конкретные отсутствующие или противоречивые источники;
- не исправляй документы и не угадывай результат.

## Read-only rules

Во время `/stage-status` запрещено:

- менять application code, `package.json`, зависимости, Prisma schema или Docker configuration;
- менять любые проектные документы;
- создавать, изменять или удалять checklist;
- менять `ROADMAP.md`, `ROADMAP_VISUAL.md`, `BACKLOG.md`, `CURRENT_STATE.md` или `DECISIONS.md`;
- выполнять build, lint, tests или runtime-проверки вместо чтения уже зафиксированных результатов;
- выполнять `git add`, commit или push;
- придумывать проценты прогресса, ETA, даты, проверки или решения.

При расхождении источников команда только сообщает о проблеме. Source of truth остаются соответствующие проектные документы.
