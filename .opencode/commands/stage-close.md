# /stage-close Command

## Назначение

Проверить Definition of Done текущего крупного этапа и либо закрыть его на основании фактов, либо показать незавершённые обязательные пункты.

## Workflow

### 1. Определить текущий этап

- Прочитай `AGENTS.md` и обязательные context-файлы.
- Определи этап по разделу **«Текущий фокус»** канонического `docs/ROADMAP.md`.
- Сверь его критерий завершения, зависимости и фактический статус.

### 2. Найти checklist

- Найди единственный checklist этапа в `docs/checklists/` по его двузначному номеру.
- Если checklist отсутствует, не закрывай этап: сообщи об ошибке процесса и предложи сначала выполнить `/stage-start`.
- Не создавай новый checklist во время закрытия только ради формального прохождения процесса.
- Убедись, что checklist отдельно содержит разделы **«Что тестирует агент»** и **«Что пользователь тестирует вручную»**.

### 3. Сверить реализацию

Сопоставь фактическую реализацию с:

- checklist;
- критерием завершения `docs/ROADMAP.md`;
- `docs/CURRENT_STATE.md`;
- `docs/BACKLOG.md`;
- `docs/ARCHITECTURE.md` и `docs/DECISIONS.md`;
- релевантным кодом.

Для каждого значимого результата используй один из статусов:

- `Verified`;
- `Build-Verified`;
- `Runtime-Verified`;
- `Not Verified`;
- `Not Applicable`.

### 4. Выполнить автоматические проверки

Как минимум выполни:

```bash
npm run build
npm run lint
```

Запусти тесты, если они существуют или требуются checklist/этапом. Не заменяй проваленные или отсутствующие проверки успешной сборкой.

### 5. Проверить разделы агента и пользователя

- Runtime-пункт отмечается выполненным только после фактической проверки.
- Build Verification не доказывает работу Telegram, БД, внешнего API, UI или другой интеграции.
- Выполни доступные агенту проверки из раздела **«Что тестирует агент»**.
- Для раздела **«Что пользователь тестирует вручную»** дождись явного результата пользователя; не выполняй и не подтверждай эти пункты от его имени.
- До получения результата не обновляй статус этапа на `✅ Завершено`.

### 6. Проверить Decision Gate и Definition of Done

Убедись, что:

- обязательная реализация завершена;
- build, lint и применимые тесты проходят;
- обязательные runtime-проверки выполнены;
- пользователь подтвердил обязательные пункты ручной проверки;
- все обязательные пункты checklist закрыты;
- нет незадокументированных значимых архитектурных решений;
- документация готова к синхронизации;
- `git diff` просмотрен.

Подтверждение пользователем ручного раздела не является командой закрытия само по себе. До запуска `/stage-close` или отдельного явного запроса «закрой этап» roadmap и статус этапа не переключаются.

Если во время ручной проверки найден дефект, не используй результаты прежней финальной проверки автоматически: открой затронутые пункты, дождись исправления и повторной проверки, затем заново выполни применимые build/runtime/docs/diff gates.

### 7. Обработать результат

Если обязательные пункты не выполнены:

- не меняй статус этапа на `✅ Завершено`;
- перечисли незакрытые пункты и их фактические статусы;
- укажи конкретные следующие действия;
- не маскируй отсутствие Runtime Verification успешным build.

Если все обязательные пункты выполнены:

1. Отметь checklist завершённым.
2. Синхронизируй `docs/CURRENT_STATE.md`.
3. Синхронизируй `docs/BACKLOG.md`.
4. Синхронизируй `docs/PROJECT.md`, `docs/ARCHITECTURE.md` и `README.md`, если изменились пользовательские возможности, структура, data flow, интеграции, запуск или конфигурация.
5. Проверь затронутые закрытые checklist: stage-specific исторический scope сохраняется, но ложные утверждения о текущем поведении обновляются или помечаются как заменённые следующим этапом.
6. Сначала обнови канонический `docs/ROADMAP.md`.
7. Затем синхронизируй `docs/ROADMAP_VISUAL.md`.
8. Обнови `docs/DECISIONS.md`, если появились новые принятые решения.
9. Если менялись конфигурация, зависимости или запуск, сверь `.env.example`, Docker-конфигурацию и package scripts.
10. Выполни поиск устаревших placeholders, статусов, названий этапов и дублируемых точных значений; проверь локальные Markdown-ссылки.
11. Проверь финальный `git diff` после всех исправлений документации.

Пункт «документация синхронизирована» можно закрыть только после этого применимого repository-wide аудита. Если часть поверхностей неприменима или не проверялась, явно укажи это в отчёте и не используй формулировку «все файлы синхронизированы».

### 8. Выдать Stage Close Report

Используй формат:

```text
Stage:
Result:
Build:
Lint:
Tests:
Agent verification:
User manual verification:
Checklist:
Docs synchronized:
Remaining issues:
Next stage / milestone:
```

## Rules

- Не закрывай этап без checklist и выполненного критерия завершения.
- Не утверждай Runtime-Verified без фактической runtime-проверки.
- Не закрывай этап автоматически только на основании сообщения пользователя о результате ручной проверки.
- Не выполняй commit или push без явного запроса пользователя.
